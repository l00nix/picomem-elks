# PicoMEM long-name USB development status — 2 November 2026

I am developing this experimental ELKS integration as l00nix, with coding
assistance, and testing it on an Amstrad PPC512 with PicoMEM 2. The hardware
test results below remain the 2 November baseline. Upstream feedback
has since arrived; the 3 November follow-up below records the next validation
work. This is a tested development candidate, not a release or a claim that all
faults are fixed.

## What has been tested

The paired firmware/kernel supports USB reads and writes, creation, append,
truncation, deletion and guarded same-directory regular-file rename with ASCII
long names up to 26 bytes. Existing destination replacement is refused. Internal
PicoMEM SD mounts remain read-only. Tests used one directly connected USB disk.

Nine media have completed guarded ELKS–Mac–ELKS data checks, including a USB-to-SD
adapter. DOS 8.3 compatibility also passed on that adapter/card with the current
firmware. I preserved file hashes and read-only FAT checks, and recorded macOS
index/log changes separately. The final warm-reboot copy/rename/delete and
unmounted reconnect test also passed.

Each medium below completed 18 native workload batches, a 30,642-byte long-name
FTP upload, full-byte checks after remount, independent Mac file verification,
a read-only FAT consistency check and an ELKS return check. All nine used the
same firmware and kernel candidate. The generic stick's earlier failure remains
part of its record even though the later workload passed.

macOS initially mounted some media read/write before the verified read-only

The DataTraveler G3 with inconsistent filesystem metadata is excluded from this
nine-media acceptance count.

DOS testing on the USB-to-SD card checked five files through their 8.3 aliases,
then create, append, truncate, rename and delete operations in a fresh directory.
A retained DOS-created file and the five earlier files matched after returning
to ELKS; independent Mac file checks and the read-only FAT check also passed.
This validates legacy DOS access, not native DOS long filenames.

The final generic-stick check followed `shutdown -r`, a warm reboot rather than
a full power cycle. Native copy and rename of a disposable 3,073-byte long-name
file passed full readback, followed by deletion and removal of its test directory.
An existing 30,642-byte file matched after remount. After a safe unplug/reconnect,
three reference files (35,449 bytes) matched and the test directory remained
absent. USB was safely unmounted; the kernel reported no latched error.
Two earlier test-harness status assertions stopped before writes; their records
were retained, and the corrected write workload ran once.

## Remaining limitations and open failures

- One generic-stick read stopped at 366,592 of 524,288 bytes and was followed by
  ELKS I/O errors. Subsequent independent Mac checks passed. Later bounded ELKS
  checks, including repeated complete reads of that file, did not reproduce it.
  Its cause remains unresolved; passing retries do not establish a fix.
- A separate FTP connection timed out waiting for its greeting, before login or
  a file request. The kernel remained healthy and a later connection succeeded
  without restarting ELKS or FTP. This is distinct from the mid-file USB failure.
- The experimental cache policy records assumed write-through when supported
  checks cannot establish cache settings. That does not prove write caching is
  disabled. blueFLIP reported write-through; the other eight used the explicit
  assumption. No power-loss durability claim is made.
- The tested scope excludes removing mounted media, simultaneous multi-disk
  mounts, full Unicode, arbitrary-length filenames and exFAT read/write.
  Safely unmounted swaps have been tested. Internal SD writes remain disabled.

## Follow-up — 3 November 2026

I clarified that `picofs` sends file-level requests directly to PicoMEM, without
using the ELKS BIOS/AT block-device path or adding a block driver. ghaerr
recommended explicitly selecting `mount -t picofs` and avoiding filesystem
autodetection. The current integration explicitly selects `FST_PICOFS` and
handles the USB/SD source before normal block-device lookup.

[Architecture reply and planned validation](https://github.com/ghaerr/elks/discussions/2841#discussioncomment-19375606).

The next checks are nested-directory operations with stack measurements,
resource exhaustion/reuse, explicit mounting and unmounting, read-only
protection, filename and rename boundaries, and fault handling. Disk-full and
transport-failure injection should start on disposable images or host fixtures.
The intermittent USB read failure and separate FTP greeting timeout remain
open. These are planned checks, not additional completed hardware results.

The repository is public. I can share the existing utilities and development
results now, while the complete long-name candidate still needs a reproducible
source/build package and focused upstream submissions. No new release or
firmware/kernel binary accompanies this documentation follow-up.
